# 08 剧本、对话与港口建筑（设施）的实现

本篇回答三个具体问题：剧情怎么编、对话怎么存、港口地图上的「房间」（设施/建筑）怎么定义。

## 8.1 剧情：SNR 脚本字节码

每个剧本 = `SNRn.DAT`（脚本）+ `SNRn.MES`（台词），n=0 共通/序章，n=1–6 六位主角。

### 容器层
```
SNRn.DAT:  "SNDT" + u16 剧本号 + 0x10 起 BE32 分节偏移表（0xFFFFFFFF 终止）
           SNR1 有 6 节（≈章节），SNR0 有 13 节
```

### 分节内部：事件入口表 + 字节码
每节开头是一张 **(事件号, 节内偏移) 跳转表**，`FF FF` 终止。以 SNR1 第 0 节为例（节内偏移均升序）：

```
00 06 08 42  FF FF              ← 节头（含表长/边界 0x0842）
0007→002C  0001→0264  0005→03CC  000A→03E2  0002→055F
0003→05A4  0000→0749  0009→077C  00FF→07C7  A001→083A
FF FF FF FF                      ← 表结束，后接字节码
```

主程序按「当前章节 + 触发条件（进港、进设施、日期、旗标）」查这张表，跳到对应偏移开始解释执行。事件号高字节带标志（如 `A0xx`），推测区分自动触发/进门触发等类型。

> **✅ 分节布局逐字节定型（2026-06-08，逆向全 7 档）**：分节起头是一个**头块**，其首 BE16 字 = 头块自身字节长 `N`（实测 `N = 2·数据字数 + 4`，含末尾 `FF FF`），中间 `(N-4)/2` 个 BE16 数据字语义未定（原样保留）。头块之后才是 `(事件号:BE16, 入口偏移:BE16)` 对表，`FF FF FF FF` 终止。**事件入口偏移以「头块之后」即 `分节起始+N` 为基准**——首事件偏移恰等于对表字节长、正落在字节码首指令上（SNR1 节0：事件 `0007→0x2C` 落在对表后第一条 `AD`）。参照实现 `converter/koukai2/snr.py` 的 `decode_section/decode_script`，产 `snr/snrN.json`（事件表 + 线性反汇编步序，事件入口精确映射到指令下标）。步为**自描述**：`op` 是大写十六进制串（`"CC"/"C8"/"FE"…`，与本文指令命名一致），已验证语义解出具名字段 `C8→line`(台词号)、`CC→face`(头像号)，其余原样保留 `args` 字节（无损可追溯）。例：`{"op":"CC","face":6}, {"op":"C8","line":0}, {"op":"C7"}`。
>
> **运行时解释器已实现（Godot sim 层，见 CLAUDE.md M5）**：从事件入口走 steps，产对话节拍 `C0 开窗 / CC 换头像 / C8 取台词 / C7 等待`；条件/未知操作码（AC/AD 及未解）**取直落分支跳过**，`FE` 当**对话块终止**——故每个事件目前演**单段线性对话**。实证：真 SNR1 节0 事件 `0007` 解出「管家麥克：若昂，很對不起，公爵有令，不許您進家門。」($n 已代入)。
>
> **FE 疑为跳转（待逆向，M12）**：该事件末尾为 `FE 02 62`，操作数 `0x0262` 紧邻下一事件 `0001→0x0264` 的入口——强烈指向 `FE = 跳转到 base 相对偏移`，是把多段「你来我往」对话串起来的机制。逆出 FE/AC/AD 语义后，解释器即可演多段分支对话（UI 与 converter 产物不变，只扩 `SnrInterpreter`）。

### 字节码指令（已实证的部分）
对节内字节码的统计验证：SNR1.MES 共 1176 条台词，SNR1.DAT 中 `C8` 指令恰好出现 1174 次、操作数 99.4% 落在 [0,1176) ——**每条台词正好被一条 C8 指令引用一次**。

| 指令 | 含义 | 证据强度 |
|---|---|---|
| `C8 nnnn` | 显示 MES 第 n 条台词 | 已验证（计数 1:1，操作数范围吻合） |
| `CC nnnn` | 设定说话人头像（n = KAO.LZW 头像号，99% < 256） | 已验证（范围吻合） |
| `C7` | 台词段结束/等待按键（几乎总是紧跟在 C8 操作数之后） | 高置信 |
| `C0 0k` | 开窗/演出控制（常见于 CC 之前） | 推测 |
| `AC/AD xx yyyy` | 条件判断/旗标操作（成对出现于分支处） | 推测 |
| `FE`, `0F/0C…` | 跳转/演出类 | 未解 |

> 典型台词序列（SNR1 节 1 实录）：`CC 0013, C8 00CF, C7, C0 02, CC 0000, C8 00D0, C7…` —— 换头像→说一句→等待→换头像→说下一句，台词号 0xCF、0xD0、0xD1 顺序递增，正是一段你来我往的对话。

> **字节码普查交叉验证**（`converter/koukai2/snr.py`，对全部 7 个 SNR 字节扫描，实测）：
> 各操作码字节数与 MES 台词数高度同频。以 SNR1（MES=1176 条）为例：C8=1174、C7=1177、
> C0=1178、CC=1081，即 C7/C0 同样近 1:1 出现于每条台词——这把 C7（等待）从「高置信」、
> C0（开窗）从「推测」进一步坐实为对话三件套 `C0 开窗 / C8 取台词 / C7 等待` 的固定节拍。
> C8 操作数 99.4% 落在 [0,1176)、CC 操作数 99.2% 落在 [0,256)（均按 BE16 读取）。
> 普查产物：`convert.py` 输出 `snr_census.json`（指令直方图 + C8/CC 操作数范围 + 静态遍历）。

## 8.2 对话文本：SNRn.MES 格式

```
头部: BE32 偏移表（表大小 = 第一条偏移；SNR1 = 1176 条）
每条: [「说话人名」0x0A] 正文 …… 0x00 终止
```

控制码（已从实际消息中确认）：

- `0x00` 消息终止；`0x0A` 换行
- `0x24 xx`（ASCII `$n`/`$s`…）：**变量替换**——`$n` 插入玩家命名的主角名，`$s` 插入另一动态名（船名/对方名）。说话人名里也可用（如「$s的随从」）
- `0x81 62 … 0x81 63`：括号对，首行包住说话人名——对话窗的名字栏即由此渲染
- ASCII 数字 `0-9`、`!`、`.` 直接单字节使用
- 其余为双字节字模索引（自定义编码，见文档 07 §7.5）；标点 `0x8131(逗)、0x8134(句)、0x8138(？)、0x8139(！)` 的低字节比标准 Shift-JIS 同类标点小 0x10，可作破解整张码表的线索

系统级文本同理：MESSAGE.DAT（1022 条，BE16 表）、MENU.DAT（61 条）、ITEM.MES（`\n\0` 分隔）。

```

PORTCHIP.LZW  7 组文化圈图块库：每组 240 个 16×16 图块（128 B/块，
```

### 进门之后：设施场景的合成

设施内部不是 tile 地图，而是**合成场景**：

1. **背景**（柜台/房间装潢）：GRAPH.DAT（65 块界面图形库）
2. **店主/职员动画**：IAP1–6.LZW + IAE1.LZW。每文件 35 块 = 7 种设施 × 5 块（1 个基础姿态集 + 4 个动作差分集）。**IAP1–6 对应 6 种文化圈的店员形象**（此前文档 05/07 误写为「对应六主角」，已更正）。块内是带目录的精灵图集：

```
块结构: N 条 8 字节目录 + 精灵数据
目录项: x(格), y(像素), w(格), h(像素), BE32 数据偏移
精灵:   8 像素单元 4 平面交错位图（同 KAO 格式）
```

已实证渲染：IAP1 块 0 含 6 个精灵，但它们是**同一人物的不同姿态帧**（sprite0 即完整待机立姿，其余为挥手/迈步等动作帧），非单图层叠贴。透明用**色键**（精灵角点色，IAP1 为索引 8 的灰）。

> ✅ **已裁决（2026-06-07，里斯本酒馆实机截图）**：设施画面 = 左上角一幅**带画框的店主画**（店主+柜台+房间装潢合成在一张图里，酒馆为头巾老板娘持酒瓶）+ 壁纸底纹 + 右侧菜单。画面中**没有**玩家立绘，也没有 IAP 风格的站立人物。
> 因此：**店主画像在 GRAPH.DAT**；**IAP1–6 = 六位主角的事件场景立绘**（剧情画面用，IAP1=若昂金发蓝衣），**IAE1 = 剧情同伴**（红发男子，疑若昂线大副）。原 convert_iap 的「文化圈店员」映射不成立，需返工为「主角编号→IAP 文件」。
>
> **店主画像 = GRAPH.DAT 块 6–21**：恰好 16 个 **136×112** 块（≈截图实测画框内尺寸 138×110），压缩后 2.8–5.3 KB。已实机收集六张已知明文：酒馆（头巾老板娘持酒瓶）、旅馆（托盘女侍；船形招牌=槽 4）、港务局/出航所（披风水手，菜单（原文不入库））、交易所（八字胡商人，天平=槽 0）、银行（账房先生执笔记账、白领结＋钱袋书架=块 14，金色器物招牌=槽 8，菜单（原文不入库））、造船所（红头巾老船匠，背景干船坞与吊架，菜单（原文不入库））、道具屋（戴眼镜绿衣店员，地球仪/望远镜/航海器材货架=块 15，柱卷招牌=槽 9，菜单（原文不入库））、教会（白须黑袍神父，彩窗十字祭坛，十字招牌=槽 10，菜单（原文不入库））、行会（红帽眼镜老者=块 12，纹章盾招牌=槽 6，菜单（原文不入库）；块 19 海图+甲胄非行会）——共九张，证实每设施一张独立画。块→设施的次序映射待解码后确认（或继续逐设施截图比对）。其余块：2–5/23/25/27 = 640×400 全屏（港口 UI 框、标题等），28–52 = 25 个 128×96（事件插图?），53–64 = 大尺寸事件图，0/22/24/26/62 = UI 件。
> 块格式：`LE16 宽 + LE16 高 + 压缩流`；压缩算法未破——已排除：LS 位流（含恒等字典）、(n,v)/(v,n) 定长对 RLE、双字节触发计数 RLE（输出恒短 10–27%）、与屏幕截图重建明文的 10 字节级公共子串匹配（全部落空，说明字面字节不直接出现在流中，或为逐平面分流编码）。
>
> **本轮反汇编新发现**（MAIN.EXE 汇编图形库 0x600–0x950）：
> - `0x84B/0x8A6`：**壁纸填充器**——以 8 行为周期平铺 4 平面图案（设施画面的蓝船底纹即此函数绘制，图案源为 8 像素单元 4 平面交错）；
> - `0x733`：矩形 API 的裁剪边界常量 `x≤0x27F(639)`、`y≤0x18F(399)`——坐标系 640×400 再确认；
> - `0x653`：1bpp→4 平面着色绘制器（字模/文本渲染路径）；
> - 推论：图片解码器先解压到 RAM 缓冲（cell 交错布局）再走标准 blit，并非边解边写 VRAM。
> **✅ 解码器已定位（2026-06-07）：MAIN.EXE 映像偏移 0xFF4**（取字节例程 0xFDF；同库 0x132D 为姊妹变换，疑为另一方向/模式）。反汇编读出的结构解释了此前所有假设为何落空：
> 1. 头部：流内读 LE16 宽（**高位为标志位**，`bh &= 0x7F`）+ LE16 高；行宽计算 `(w+3)>>2`；
> 2. **块内嵌 16 字节（8 word）映射表**（读入 `cs:[0xBBC]`）——字面像素经表映射，直接子串匹配必然失败；
> 3. 主循环 token：bit7=0 → 一类操作（0x11EA）；bit6 → 分支 0x114D；低 4 位+1=计数、bits4-5+1=参数；
> 4. 拷贝以 **nibble（4-bit 像素）为粒度**，源/目标可错半字节（shr/rcl 对齐 + `shl al,4 / and 0xF0 / or [di]&0x0F` 合字节），输出为 **chunky 4bpp**（2 像素/字节）而非平面格式。
> 即：nibble 粒度 LZ + 内嵌映射表 + chunky 输出，三层都与此前的字节级/平面假设不同。
> **执行方案**：函数分支多、nibble 操作易转写出错 → 用仿真执行（unicorn 或针对其 ~30 条指令子集的迷你 8086 解释器），喂 GRAPH.DAT 块取输出，以 9 张实机明文截图做验收；产出 `converter/koukai2/graphdat.py`。
>
> **✅ 已破解并导出（2026-06-07）**：自写迷你 8086 解释器（`converter/koukai2/_emu8086.py`，capstone 译码）执行原 0xFF4 例程。过程中的决定性 bug：**BP/SP 相对寻址默认段是 SS 不是 DS**（修正后解码立刻正确）。两点更正前述静态推断：① 输出**不是 chunky**，而是**4 平面 cell 交错**（每 8px 单元 4 字节，与 KAO 精灵同格式，stride=⌈w/8⌉×4）；② 内嵌表为 16 字节。块 6 解出八字胡商人，与交易所截图逐像素吻合。

### 与剧情的衔接

剧本事件常以「在某港进入某设施」为触发条件：引擎进设施时查当前剧本当前章节的事件入口表（§8.1），命中则先执行剧情字节码（CC/C8/C7 对话），否则进入常规设施菜单（交易/造船/雇船员…）。这就是为什么同一家酒馆平时是菜单、剧情节点时变成事件画面。

## 8.4 角色移动模型（静态证据 + DOSBox 实机观测 + 截图测量 + 实玩确认）

**逻辑：16px 整格移动。** 一次输入移动 1 格（实玩确认）；碰撞与 ZA_DAT 设施触发按格判定。

**渲染：精灵带恒定 +8px 横向偏移，不贴齐地图格。** 截图测量（以建筑墙体图块边界为基准）：静止角色精灵左缘 = 图块边界 +8px，主角与 NPC 一致——是固定的绘制偏移（视觉上骑在两格中间），不是半格逻辑位。

> 勘误记录：本节曾先后误判为「一步=1 格、8px 仅是动画子步」与「位置格=8px」。
> 单张截图中两个角色同为 +8 相位，恰好支持「恒定渲染偏移」而非「8px 逻辑格」
> （若为 8px 逻辑格，静止相位应在 +0/+8 间混布）。

**行走动画**：一步 16px 拆成 2 个 8px 子步滑动，两帧行走帧随子步交替；精灵屏幕位置因此在字节对齐/+8 两相位间交替——CHAR.LZW 中每帧的两份拷贝（原始 + 右移 8px 预移位副本，逐像素验证 b[x+8]==a[x]）正好各承担一个相位，这是平面 VGA 上避免实时位移的预计算。镜头以同样的 8px 子步跟随（实机连拍证实）。

**节奏。** 实机观测（DOSBox-X，3000 cycles）：一格约 0.2–0.4 秒，按住方向键连续移动；NPC 用同一套系统自主游走。

**朝向。** 行走帧只有正面（向下）与背面（向上）两种朝向 × 2 步帧；左右移动复用正/背面帧（实机向右行走显示正面）——16px 窄精灵时代的省美术惯例。

**对 Godot 复刻的映射**：移动逻辑按 16px 整格；精灵节点恒定 `offset.x = +8`；一步用 2×8px 子步插值（或 0.2–0.4s tween）；镜头 8px 量化跟随。

## 8.5 小结：三件事的设计模式

| 问题 | 答案（一句话） |
|---|---|
| 剧情 | 7 份「章节→(事件号,偏移)跳转表→字节码」的脚本档，主程序是解释器 |
| 对话 | 脚本 `CC`(换头像) `C8`(取台词号) `C7`(等待) 驱动；台词集中存放在带偏移表的 MES 档，支持 `$` 变量与说话人名行 |
| 港口房间 | 地图只管美术；ZA_DAT.DAT 每港 12 个设施门口坐标才是逻辑；进门后切到「背景图+店员精灵差分动画+对话窗」的合成场景 |
